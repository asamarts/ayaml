## Why

Issue #191. The compatibility reader keeps a tag outside the core schema on its node, and hands
the node to a target as an enum whose variant names the tag. A libyaml-based reader keeps only a
tag written with a local `!`, and drops every global one: a scalar beneath `!!timestamp` is its
text to a target that reads any value, and the number it spells to a typed one. So documents
that such a reader decodes are refused here, for a target that buffers through
`deserialize_any`, and for a typed scalar or a struct beneath a `!!` tag that the core schema
doesn't define. A struct beneath a tag written out in full, as `!<tag:example.com,2000:x>`, is
read. The refusal of `!!foo {a: 1}` for a struct says `invalid type: map, expected struct S`,
which names the node's kind where the tag is what stands in the way. Keeping the tag is right for the default reader and for a caller that reads
`Value::Tagged`, so the default stays.

A caller can rebuild part of the old rule in a deserializer of its own over
`compat::from_str_seed`, and one does. It can't reach the two places the node reader settles
before it shows the tag. The default reader takes a seed through `Deserializer::next_seed` and
`from_value_seed`, and has no `from_str_seed` as the compatibility module has.

## Acceptance criteria

- [x] the compatibility API has an opt-in that drops a global tag: a scalar beneath it reads as its text for a target that reads any value and as the requested type for a typed one, a collection beneath it reads as if it had no tag, and a local tag keeps today's reading
- [x] the opt-in is taken by a typed entry point and by its seed form, and reads the same from a tree and from events
- [x] the default reader has a `from_str_seed` and its `_with_limits` form, as the compatibility module has
- [x] the refusal of a node for its tag names the tag
- [x] the issue's documents read as it says a libyaml-based reader reads them, and the default readers are unchanged
- [x] the shape of the options value is the one AY-048 settles, or is settled here and AY-048 follows it
