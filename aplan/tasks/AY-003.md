## Why

A malformed flow collection can fail in two ways, and neither parser says both where it failed
and where the collection began.

- The root parser names the failure and not the opening when an unexpected token follows a value.
  When the input ends inside the collection, its one location is the opening, or the start of the
  input, which is neither, when it was looking ahead for the end of an entry.
- Compat names the opening only when it expected `,` or a closing bracket. It finds the opening by
  searching back through the text, so it can name a bracket inside a quoted scalar. Its other flow
  failures, and input that ends inside a collection, name no opening.

The wording stays human text, and a structured secondary span belongs with later diagnostics
work.

## Acceptance criteria

- [x] in both modes, malformed flow sequences and mappings report the failure and the opening location, including when input ends inside the collection and when an unexpected token follows a value
- [x] the opening comes from parser state, so a bracket in a quoted scalar, or one that has already closed, is never named
- [x] the message says whether the collection is a sequence or a mapping, and compat words every one of these failures as it already words the failure that names an opening
- [x] the primary span is the failure location in both modes, including at the end of the input
- [x] nested flow forms, quoted delimiters, CRLF, BOM, and multibyte UTF-8 have regression tests
- [x] default and compatibility modes retain their separate semantic profiles
