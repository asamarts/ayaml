## Why

AY-109 gave whole block entries a span and tested shapes chosen by hand. An audit deleted every
span a tree gives on a corpus of documents and read the rest: about 3% of the spans changed
something else. What is exact for an entry depends on the lines around it, which the hand-picked
shapes did not vary. This is in no release.

## Acceptance criteria

- [x] a key after a `?` on an earlier line, a key that isn't on one line with its `:`, and a key with no text have no entry span
- [x] an entry before a line that begins with `:` has none
- [x] an entry inside a collection that has an anchor has none
- [x] the only entry of a collection has none, so no entry span leaves a collection empty
- [x] an entry after a block scalar has one only when content follows it directly, wherever the scalar is, a key included
- [x] a value has the span of a missing one only when the source shows none after the `:` on its key's line; a node that ends in a scalar with no text has no known end
- [x] on generated documents that put every kind of entry next to every other, each span a tree gives is deleted and the rest read, in both modes, and the test counts the spans it checked
- [x] the hand-picked tests run in both modes and check each span by deleting it
- [x] D92, the design note, and the changelog state the rule as it is
