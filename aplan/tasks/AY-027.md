## Why

Compat classifies errors by matching their message text, so user input can change
an error's kind. Some errors carry the wrong location or none.

`parse_events` and the `Deserializer` read a stream a document at a time, so with problems in
more than one document they can report an earlier one than the readers that scan the whole stream
first. `docs/limits.md` says so for limits, and it holds for other errors too.

## Acceptance criteria

- [x] compat classifies by structured error data, never message text, with tests using hostile key names
- [x] the structured data is a private per-failure code that a later release can publish without reclassifying
- [x] an unterminated flow collection does not report line 1 column 1 on later lines
- [x] an implicit null at end of input carries a correct span, as does one at the end of a document in a lazy read, which `event_places_match_their_offsets` checks
- [x] lazy stream-start and stream-end events carry the spans the eager event reader gives them, which AY-026's `lazy_and_eager_events_match` checks
- [x] an input reports the same first error, at the same line and column, on every reader in a mode
- [x] duplicate-key location survives keys containing location-like text, and complex keys print readably
- [x] a complex key's message stays short whatever the key's size, and shows no internal type, nor does a tagged key's: `!t 1: a\n!t 1: b` prints the key's node from `from_str`
- [x] typed readers and `parse_value` point at the same occurrence of a duplicate key
- [x] a typed map in default mode either keeps keys that differ only in type, as `1` and `"1"` do, or reports them; it doesn't drop one silently
- [x] composer depth errors and `next` errors carry spans
- [x] compat decides an error by what the parser reports, not by the input's text: an input that starts with a byte order mark and then `%` reports "found character that cannot start any token" with no location, whatever its error is, as in `\u{feff}%YAML 1.2\n---\na: 1\na: 2\n`
- [x] compat's depth and document-count errors carry the location of what they report, as default mode's depth error does at line 129 column 257 for 129 nested block sequences, and a read of one document reports an error inside it, such as a duplicate key, before it reports that a second document follows
- [x] a limit that the scanner checks while it reads ahead doesn't hide an earlier error, in either mode: `}-x` followed by a line of 300 `[` reports the `}` at line 1 column 1, as `}-x` alone does
- [x] a missing `:`, an entry indented less than its sequence, and a block scalar not indented past its parent are reported as such, near where they are, not as unexpected content after the document, as `- key: first\n\n  second\n`, `a:\n  - b\n - c\n`, `-\n|2 `, and `? \n|` are today
