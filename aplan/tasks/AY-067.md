## Why

Compat follows libyaml in some places and YAML 1.2.2 in others, and the two can meet badly: it
takes a character by one rule and what follows by the other, and refuses text that default mode
and libyaml each read. A drop-in reader shouldn't refuse what both of the readers it stands between
accept. The forms are rare, and each came from generated or mutated input.

## Acceptance criteria

- [x] a flow `?` before `-` or before a tag with a `!` in its suffix doesn't fail in compat: `[?-]`, `{?-}`, and `[?!!!,]` read as libyaml reads them
- [x] an anchor name that stops in compat doesn't leave a `?` or `:` that fails where default mode reads the name whole: `[&a:a?]`, `{&a:b?}`, `&a\u{85}?`
- [x] a block scalar under an anchored `:` key at the parent's indent reads in compat: `&a::\n|`, `&a::\n|\n x`
- [x] a name that holds its `:` before NEL, LS, or PS reads in compat as it does by default, or the difference is documented: `&a:\u{85}\n  ---`, `&a:\u{85}\n  b: c`, and `&a:\u{85}\n  b`, which compat reads as `":\u{85} b"`, and `&::\u{2028}`, which compat reads as `":\u{2028}"` and default mode as null, and `&":\u{85}`, which compat reads as `":\u{85}"` where libyaml refuses the name
- [x] a NEL in a comment after a flow `?` doesn't fail in compat: `{?# \u{85}}`
- [x] outside a flow collection, a `:` before a flow indicator ends a name in compat, as a `:` before other text does and as in libyaml, so `&r:}` reads the string `:}`, or the refusal is documented
- [x] a document marker after a byte order mark and a line break character reads as it does by default: `\u{feff}...\n...\u{2028}`
- [x] a `#` right after a flow `?` reads in compat as libyaml reads it, as a comment after an indicator, or the refusal is documented: `{?#\n}`, `[?#\n::]`
- [x] a mark that starts a key's line doesn't make compat's own indent check on a quoted scalar below it stricter, so `# c\n\u{feff}k:\n  'a\n b'` and `# c\n\u{feff}k:\n  ['a\n b']` read in compat, as libyaml and default mode read them: the mark's column puts `k` at column 1
