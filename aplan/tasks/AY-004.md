## Why

The 0.1.1 bytes, tag, checksum, and VCS identity agree, but publication is
manual, workflow dependencies are mutable, and the release asset has no
keyless provenance. A security dependency should make its publication chain
independently verifiable. adotenv's `release.yml` and `RELEASING.md` are a working
starting point.

## Release record

On 2026-11-14, the `v0.1.2` tag (commit `4c70a005fce2469a15ca006a33673e0933f69902`) published
`ayaml-0.1.2.crate` through the `release` environment and crates.io Trusted Publishing. The
workflow verified the package and registry bytes, created the GitHub release with `SHA256SUMS`,
and produced an attestation that verifies with the command in `RELEASING.md` and AY-005. Crate
sha256: `c8fa4b10832a9ec125b53aa3c63f75914d52f3e96b49a4e4ecad96d0afc18dfa`.

The remaining setup step is to enable "Trusted Publishing only" on crates.io and revoke the
legacy API tokens that could publish `ayaml`. That is the last open criterion.

## Acceptance criteria

- [ ] every action is pinned to a full commit SHA with a maintained version comment, including the secret-scan action, and installed CI tools have pinned versions
- [x] the manual crates.io Trusted Publisher and GitHub environment setup is done and documented in `RELEASING.md`
- [x] a least-privilege OIDC workflow publishes through crates.io Trusted Publishing without a long-lived token
- [x] tag, version, commit, package contents, registry bytes, release asset, and checksums are bound and verified
- [x] the release asset carries a verifiable GitHub SLSA provenance v1 attestation
- [x] rerun, partial-failure, sparse-index wait, and immutable-post-publication recovery procedures are documented, including a tag or version that can't be reused
- [x] the workflow refuses a tag whose commit is not on `main`, and never publishes from a pull request, a fork, a mutable branch head, or a dirty checkout
- [x] the workflow runs the release gate before publishing, and verifies packaged source against the tag
- [x] the release record gives the workflow, issuer, repository, ref, commit, artifact name, and digest a consumer needs to verify the attestation
- [x] required checks are updated for any renamed or added jobs
- [ ] after the first release through the workflow, crates.io accepts only Trusted Publishing for `ayaml`, and no API token that could publish it is left, as `RELEASING.md`'s third setup step says

## Status

The workflow, its checks, and `RELEASING.md` are in place. The `release` environment exists,
limited to `v*` tags with the owner's approval, and immutable releases are on. The crates.io
Trusted Publisher was registered on 2026-11-08 for the repository, workflow, and environment
that `RELEASING.md` names, and crates.io's API lists it. The first release through the
workflow is the first to use it. After that release, `RELEASING.md`'s third step turns on
"Trusted Publishing only" and revokes the API tokens.

The third through fifth criteria and the release-record criterion passed on the first real
workflow release, `v0.1.2`; the record is above. A workflow-dispatch rehearsal against `v0.1.1`
had already passed on 2026-11-12, including the draft creation, check, cleanup, and the script's
`release` command against a fake gh. The remaining work is the one-time crates.io switch to
Trusted Publishing only and revoking the legacy publishing tokens.

Every action is pinned to a full commit with the release it is, and `tools/test_ci_checks.py`
fails on any other pin, in a workflow or a local composite action, and on a secret scan image
whose tag isn't the action's version. The scan's job checks that the image's digest reports
that version. Dependabot moves only the action, so the image is updated by hand in the same pull
request. cargo-deny, cargo-semver-checks, gitleaks, and the Rust toolchains that the release and
the semver checks use are pinned by version, and the downloaded binaries by checksum. The first
criterion's open part is two packages from Ubuntu's signed archive, valgrind for the instruction
counts and age for fuzz crashes, which follow the runner image's version. Neither decides a
result by its version: the counts compare two builds under the same valgrind in one job, and
age only encrypts. Whether that closes the criterion is the owner's decision. The other
toolchains are stable and nightly on purpose.

No job was added to or renamed in `ci.yml`, so the required checks are unchanged.
