## Why

The 0.1.1 bytes, tag, checksum, and VCS identity agree, but publication is
manual, workflow dependencies are mutable, and the release asset has no
keyless provenance. A security dependency should make its publication chain
independently verifiable. adotenv's `release.yml` and `RELEASING.md` are a working
starting point.

## Acceptance criteria

- [x] every action is pinned to a full commit SHA with a maintained version comment, including the secret-scan action, and installed CI tools have pinned versions
- [ ] the manual crates.io Trusted Publisher and GitHub environment setup is done and documented in `RELEASING.md`
- [x] a least-privilege OIDC workflow publishes through crates.io Trusted Publishing without a long-lived token
- [x] tag, version, commit, package contents, registry bytes, release asset, and checksums are bound and verified
- [x] the release asset carries a verifiable GitHub SLSA provenance v1 attestation
- [x] rerun, partial-failure, sparse-index wait, and immutable-post-publication recovery procedures are documented, including a tag or version that can't be reused
- [x] the workflow refuses a tag whose commit is not on `main`, and never publishes from a pull request, a fork, a mutable branch head, or a dirty checkout
- [x] the workflow runs the release gate before publishing, and verifies packaged source against the tag
- [x] the release record gives the workflow, issuer, repository, ref, commit, artifact name, and digest a consumer needs to verify the attestation
- [x] required checks are updated for any renamed or added jobs

## Status

The workflow, its checks, and `RELEASING.md` are in place. The `release` environment exists,
limited to `v*` tags with the owner's approval, and immutable releases are on. The second
criterion waits for an owner to register the crates.io Trusted Publisher, as `RELEASING.md`
says. The publish, attestation, and release jobs first run for real at the next release. A
run started by hand rehearses the rest against a published tag.
No job was added to or renamed in `ci.yml`, so the required checks are unchanged.
`tools/test_ci_checks.py` fails on an action used by anything but a full commit with its
version, and on a secret scan image whose tag isn't the action's version. Dependabot moves
only the action, so that image is updated by hand in the same pull request.
