## Why

The 0.1.1 bytes, tag, checksum, and VCS identity agree, but publication is
manual, workflow dependencies are mutable, and the release asset has no
keyless provenance. A security dependency should make its publication chain
independently verifiable. adotenv's `release.yml` and `RELEASING.md` are a working
starting point.

## Acceptance criteria

- [ ] every action is pinned to a full commit SHA with a maintained version comment, including the secret-scan action, and installed CI tools have pinned versions
- [ ] the manual crates.io Trusted Publisher and GitHub environment setup is done and documented in `RELEASING.md`
- [ ] a least-privilege OIDC workflow publishes through crates.io Trusted Publishing without a long-lived token
- [ ] tag, version, commit, package contents, registry bytes, release asset, and checksums are bound and verified
- [ ] the release asset carries a verifiable GitHub SLSA provenance v1 attestation
- [ ] rerun, partial-failure, sparse-index wait, and immutable-post-publication recovery procedures are documented, including a tag or version that can't be reused
- [ ] the workflow refuses a tag whose commit is not on `main`, and never publishes from a pull request, a fork, a mutable branch head, or a dirty checkout
- [ ] the workflow runs the release gate before publishing, and verifies packaged source against the tag
- [ ] the release record gives the workflow, issuer, repository, ref, commit, artifact name, and digest a consumer needs to verify the attestation
- [ ] required checks are updated for any renamed or added jobs
