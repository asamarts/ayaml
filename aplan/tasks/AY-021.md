## Why

Typed decoding accepts input that does not match the target, producing values the
caller did not write. `from_value` also rewrites scalars into strings. Its rules have
to match `from_str` on null, booleans, and variant names too.

## Acceptance criteria

- [x] float targets accept only core-schema spellings and finite parsed values; other text, and a scalar tagged as a string, is an error, on every reader: `inf`, `1e999`, `!!str 1.5`, and `! 5`, which `a_float_target_reads_only_numbers` checks
- [x] a sequence does not decode positionally into a struct
- [x] a bare variant name does not fill a data-carrying variant
- [x] `from_value` into a string target rejects non-string values, and its API docs say so
- [x] `from_value` and stream decoding treat null like `from_str` for sequence, mapping, struct, and struct variant targets, tagged or not, rather than filling in an empty or default value: `~`, `!list ~`, and `Point: ~` differ today
- [x] `from_value` selects an enum variant by its exact name, not by a value that merely reads the same
- [x] `from_str`, `from_str_borrowed`, `from_value`, seeded, and compat paths agree or differ only as documented
- [x] a tag's `handle()` and `suffix()` don't depend on which reader produced it
