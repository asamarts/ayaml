## Why

Callgrind profiling shows five major CPU and memory bottlenecks across the scanner, parser,
and core value/event representations:

1. **Bloated `Error` (104 B) and `Tag` (48 B):** `Result<_, Error>` is 104 B on the stack
   across every internal hot function (`next_token`, `call`, `resume`, `emit`, `deserialize_*`),
   forcing hidden `sret` memory traffic on every call, while inline `Option<Tag>` (48 B) bloats
   `Event` (144 B), `Call` (128 B), and `Frame` (264 B).
2. **Eager 2-pass `LineStarts` pre-scan and per-scalar `walk_line` rescan (`position.rs`, `scanner.rs`, `scanner/scalars.rs`):**
   Every parse scans the full input twice before token 1 to build `Arc<Vec<usize>>` `LineStarts`
   (160 to 412 KiB on large shapes, ~2% of total instructions on every document, and 2 extra
   allocations even on error-free parses, plus 2 more allocations when `clear_parser_storage`
   resets it), and `scan_plain` calls `has_block_prefix` -> `walk_line` to rescan from column 0
   on every block value.
3. **Byte-by-byte scalar scanning (`scanner/scalars.rs`):** Plain, quoted, and block scalars
   advance one byte at a time instead of word-at-a-time SWAR, capping `large-scalar-1mb` far
   below single-pass native throughput.
4. **Flow parser overhead (`parser.rs`, `parser/flow.rs`):** `flow_ends: HashMap<usize, usize>`
   allocates and SipHashes every `[`/`{` token, `flow_mapping_loop`/`flow_sequence_loop` lack
   inline scalar fast paths (unlike block mappings in `grammar.rs`), and `Cont` is ~136 B.
5. **Per-parse setup & event-copy overhead (`scanner.rs`, `parser.rs`, `resolver.rs`):**
   `Scanner` embeds two eager `HashMap`s (calling `RandomState::new()` even with zero `%TAG`
   directives) and copies 104 B `Limits` by value; `parse_int_with` runs 128-bit
   `u128::from_str_radix` for tiny integers; and `EventSink` constructs 144 B `Event` values
   even for internal streaming consumers.

## Scope

1. **Box `Tag` (48 B -> 8 B) and internal `Box<Error>` (104 B -> 8 B):**
   - Box `Tag`'s private interior (`Option<Tag>` becomes 8 B; shrinks `Event` 144 -> 104 B,
     `-28%` on `events` memory) with zero public API changes.
   - Propagate `Result<_, Box<Error>>` (8 B in 1 register) across all internal scanner, parser,
     composer, and typed hot paths while keeping `pub struct Error` / `MaskedError`
     0.2.x-compatible (deferring public `Error` boxing and dropping unreachable `const`
     qualifiers to `AY-172` for `1.0.0`).
2. **Eliminate eager `LineStarts` pre-pass and `walk_line` rescans:**
   - Validate non-printable bytes inside the scanner's existing 256-byte lookup table (only UTF-8
     lead bytes `0xC2` and `0xEF` can introduce non-printable code points in valid UTF-8).
   - Track `current_line_start`, `current_line_indent`, and `line_has_block_prefix` inside
     `Scanner` so `scan_plain` avoids rescanning from column 0.
   - Compute line/column coordinates lazily on error paths only, and remove the allocating
     `LineStarts::new("")` reset in `DocumentEvents::clear_parser_storage`.
3. **Add safe-Rust 8-byte SWAR scanning (`scanner/scalars.rs`, `scanner.rs`):**
   - Use `u64::from_ne_bytes` over `as_chunks::<8>().0` (zero `unsafe`, `#![forbid(unsafe_code)]`)
     to accelerate plain, single-quoted, double-quoted, block scalar, and comment scans.
4. **Fast-path flow parsing and compact `Cont` (`parser.rs`, `parser/flow.rs`):**
   - Replace `flow_ends: HashMap<usize, usize>` with inline `u32` partner indices on open flow
     tokens.
   - Add inline scalar fast paths in `flow_mapping_loop` and `flow_sequence_loop` matching
     `grammar.rs`'s block mapping fast path, and shrink `Cont` (`u32` offsets/lengths, ~48 B).
5. **Scanner, resolver, and `EventSink` lean hot paths:**
   - Store `Option<Box<TagHandles>>` and `&Limits` in `Scanner`.
   - Add a `<= 18`-digit `u64` fast path in `resolver::parse_int_with`.
   - Add specialized `EventSink` callbacks (`on_plain_scalar`, etc.) so internal composers and
     stream readers bypass constructing 144 B `Event` enums.

## Acceptance criteria

- [x] `size_of::<Tag>() == 8`, `size_of::<Box<Error>>() == 8` on all internal hot paths (with public `Error` boxing deferred to `AY-172` for the `1.0.0` version bump so `0.2.3` `cargo-semver-checks` stays 202/202 green), `size_of::<Event<'_>>() <= 104`, and `size_of::<Cont>() <= 64`
- [x] `large-scalar-1mb` `events` throughput increases substantially (>= 2x, surpassing 1,500 MiB/s on reference hardware; measured 4.04 GiB/s on `parse_value` and -70.95% Callgrind `Ir` / 3.44x on `events`) with zero `unsafe`
- [x] `json-in-yaml` and `depth-64` show major Callgrind `Ir` reductions (>= 25%: `json-in-yaml:events` -29.70%, `json-in-yaml:parse_value` -27.44%, `depth-64:events` -34.53%, `depth-64:parse_value` -27.02%) and zero `flow_ends` `HashMap` allocations
- [x] happy-path parsing performs zero `LineStarts` allocations (`LineStarts` is `#[cfg(test)]` only; `large-scalar-1mb:scan` drops to 0 B / 0 allocations)
- [x] full workspace tests, `--cfg ayaml_typed_from_events`, YAML Test Suite (0 deviations), Miri, Kani, and Callgrind checks pass cleanly
