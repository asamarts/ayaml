## Why

A reader of events keeps each node that has an anchor as a tree, for the aliases that may
follow it, beside the tokens and the value it is building (D95). A read that builds the whole
tree first frees the tokens before it builds the value. So a document whose nodes mostly have
anchors, as a serializer that keeps object identity writes, peaks higher from events: 95 MB
against 76 MB for 50,000 anchored flow mappings of two entries, by issue #178's measure. The
budget of `@anchored-maps-50000` holds that figure where it is. A root with an anchor is
already read with the tokens freed. The same holds for every node that is built whole and is
not the root: one with a tag that it keeps, one that an enum reads, and a key that is a
collection. A megabyte flow sequence that is a mapping's value peaks at 131 MB with an anchor or
a tag, where a read that built the tree first peaked at 99 MB, and one that is a key at 152 MB
against 114 MB.

## Acceptance criteria

- [x] a document whose nodes mostly have anchors peaks no higher than a read that builds its tree first, and the budget of `@anchored-maps-50000` is lowered to that
- [x] so does a large node inside the document that has an anchor or a kept tag, that an enum reads, or that is a key, and a budget holds one of each
- [x] the input is scanned once, whichever way it is then read, and a document with a few anchors is read from events as now
- [x] the two readers still give the same value or error, which the tests that read both ways show for the shape
