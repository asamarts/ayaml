## Why

A reader of events keeps each node that has an anchor as a tree, for the aliases that may
follow it, beside the tokens and the value it is building (D95). A read that builds the whole
tree first frees the tokens before it builds the value. So a document whose nodes mostly have
anchors, as a serializer that keeps object identity writes, peaks higher from events: 95 MB
against 76 MB for 50,000 anchored flow mappings of two entries, by issue #178's measure. The
budget of `@anchored-maps-50000` holds that figure where it is. A root with an anchor is
already read with the tokens freed.

## Acceptance criteria

- [ ] a document whose nodes mostly have anchors peaks no higher than a read that builds its tree first, and the budget of `@anchored-maps-50000` is lowered to that
- [ ] the input is scanned once, whichever way it is then read, and a document with a few anchors is read from events as now
- [ ] the two readers still give the same value or error, which the tests that read both ways show for the shape
