## Why

AY-107 kept a retyped scalar's text where the source spells it and left one case out: a value
that only an escape spells kept no text. A string target refused it, and an audit found worse: a
key of that kind fell through to its number, which a derived struct takes as a field's index, so
`!!int "0\x30": 7` filled the first field. The rule was also uneven, since a value found
anywhere in the quoted source kept its text. A typed node now keeps the decoded text too, in the
room its style took, so every retyped scalar reads as it did in 0.1.3.

The same audit found a gap older than this work. D87 says a bare variant name fills no
data-carrying variant, and `from_value` refuses one, but a reader from text read `List` as
`List(vec![])`.

## Acceptance criteria

- [x] a typed node keeps the text of a retyped scalar in every style, decoded where an escape or a block scalar spells it, and stays 80 bytes
- [x] a key names a field by its text, never by its number, whatever spells it
- [x] a bare variant name fills a unit variant and one that holds an `Option`, and no variant that holds a sequence, a mapping, or other data; a tag or a key with no value still reads as an empty one
- [x] the readers' tests cover the cursor over a stream and the seeded compatibility reader, struct targets, the scanner-first rule, and the message as well as the place
- [x] the changelog no longer lists an exception for escapes, and states the variant fix
