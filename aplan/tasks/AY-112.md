## Why

An audit of AY-105 found that its arena estimate kept two caps from before: eight tokens a line
and half the input's length. On a document of long lines, or of one, the estimate fell to the
tokens already scanned and the arena grew by a sixteenth at each fill, about fifty times for a
1 MB flow sequence where it had doubled eight times. Four of its unit tests passed on the code
they were written against, two of its claims had no test, and `docs/limits.md` gave the arena's
slot as the whole cost of a token.

## Acceptance criteria

- [x] the estimate is capped by the input's length, the token limit, and eight times the tokens scanned, and no longer by the lines; a document of even density takes five reservations at most, on short lines, long lines, or one
- [x] the estimate is worked in 128 bits, so it doesn't fall to the tokens scanned on a 32-bit target
- [x] each arena test fails when the rule it names is removed, which five single changes to the code confirm
- [x] the entry count of a root flow collection is tested on a later line, and the builder's cap at `max_collection_entries` is tested
- [x] a reader of bytes refuses input over the limit before it checks that it is UTF-8
- [x] the memory tests measure each reader in a child of its own, and where they can't measure they still check that the input is refused
- [x] `docs/limits.md` gives a token's second allocation, measures the default limit at 32 MB to about 80 MB, and says which readers use the arena
