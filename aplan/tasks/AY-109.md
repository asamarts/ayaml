## Why

`SpannedTree` computed an entry's span from its key alone. A block entry whose value continued on
later lines got only its key line, a flow entry got only its key, an item that ended in a block
scalar took the next item with it, and a value that the source doesn't write stood at the next
line's first token. A caller that deleted such a span broke the document. This is in no release.

## Acceptance criteria

- [x] a block mapping entry or block sequence item that begins its own line has a span through its last line break, with a nested value, a block scalar, and a trailing comment (AY-110 adds the conditions that the lines around an entry set)
- [x] a flow entry, an entry that shares its first line, an entry with an explicit key or a property before its key, an item with no value, and an entry that defines an anchor have none
- [x] a byte-order mark stays outside the first entry's span, and a CRLF goes with its entry
- [x] a value that the source doesn't write has an empty span right after its key's `:`
- [x] each span in the tests is checked by deleting it and reading the rest of the document
- [x] D92 records the rule
