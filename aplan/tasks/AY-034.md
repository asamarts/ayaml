## Why

`docs/limits.md` claims every check is tested just below, at, and above its limit.
Most limits are only tested far above, on one or two entry points, and several
reject-at-limit mutants survive.

AY-026 added `crates/ayaml/tests/limit_consistency.rs`: a table of inputs, each with the least
value of one limit that accepts it, run at that value, one above, and every value below, on every
reader that takes limits. It has no case for `node_cost_bytes`, and sets
`alias_bytes_per_input_byte` only to 0. This task can extend it to each place that counts, to those
two limits, and to the readers that take the default limits only.

## Acceptance criteria

- [x] a table-driven test covers each limit below, at, and above on each entry point where it applies
- [x] the entry-count limit is covered at each place that counts entries: block and flow mappings, block and flow sequences, and explicit keys, including the short-block fast paths
- [x] entries that cannot apply are stated as such in the table
- [x] reject-at-limit mutants fail, with limit-disabling mutants excluded or run under a memory bound
- [x] `docs/limits.md` describes what the table proves
